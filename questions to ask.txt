gold expectation tables: 

1. gold_ev_exceptions -> This is the row-level store that PL_04's Conditional Split writes into directly. Every single flagged record lands here.
2. gold_ev_exception_summary -> PL_04's Lookup_Exception_Rate activity queries this table, not the raw exceptions table. It's a daily rollup that PL_04 reads to decide whether to fire the Logic App alert. If we make PL_04 scan the full gold_ev_exceptions table every run, it will be slow as data grows. This summary table is what makes PL_04's monitoring query fast.
3. gold_ev_fault_timeline  -> This is the fault-specific detail table. Even though faults also land in gold_ev_exceptions, you need this separate table because the Faults & Revenue Impact dashboard page (Page 04 ) needs fault-only rows with full financial context — MTTR, downtime, lost revenue, customers lost — without filtering through the entire exceptions table every time Power BI renders a visual.

4. gold_ev_charger_exception_profile This is the per-charger health rollup. Page 06 Charger Diagnostics screenshot shows a "System Health" panel with per-component health scores and a flag for high-risk chargers. This table is what PL_04 populates so Power BI can show which chargers are most problematic without scanning row-level exceptions.

4. gold_ev_packet_drop_gaps -> 	This is the only table that captures the 1% packet drop from data_gen.py. These rows don't exist in gold_ev_exceptions because there's nothing to flag — the record simply never arrived. The gap detection logic in your stored procedure generates one row per missing minute per charger by comparing expected timestamps against what actually exists in silver.
