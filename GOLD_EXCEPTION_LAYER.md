# Gold Exception Layer — Table & Stored Procedure Reference

## Overview

The Gold Exception Layer is the analytical output of the EV Telemetry pipeline. It sits above the Silver layer (`silver_ev_operations`) and is responsible for detecting, categorising, and aggregating all data anomalies, hardware faults, and signal gaps that occur in the raw telemetry stream. This layer is what makes the pipeline **observable** — without it, bad data silently passes through to Power BI.

The layer is built from **5 tables** populated by **1 stored procedure** (`usp_Load_Gold_EV_Exceptions`), which is called by **PL_06** before **PL_04** runs its monitoring check.

---

## Why This Layer Exists

The raw telemetry data generated by `data_gen.py` intentionally simulates real-world failure conditions:

- **1% of charger heartbeats are dropped** (packet loss)
- **2.5% of billing readings go NULL** (energy meter comm gap)
- **1.8% of thermal sensor readings go NULL** (probe failure)
- **8 distinct fault types** can trigger at runtime (GROUND_FAULT, THERMAL_OVERLOAD_SHUTDOWN, etc.)

Without a dedicated exception layer, these anomalies either corrupt aggregations in Power BI or go completely undetected. The Gold Exception Layer routes all of these into structured tables so they can be monitored, alerted on, and visualised.

---

## Exception Categories

All exceptions are tagged with one of four categories:

| Category | What it captures |
|---|---|
| `NULL_INJECTION` | Fields that went NULL due to sensor/meter communication failures |
| `FAULT_STATE` | Minutes where a charger's status was `Faulted` with an active error code |
| `LOGICAL_ANOMALY` | Business logic violations — sessions with no user, repeat faults, peak-hour failures |
| `PACKET_DROP_GAP` | Missing heartbeat rows — charger went offline for ≥1 minute |

## Table Reference

---

### 1. `gold_ev_exceptions` *(existing table — altered)*

**Purpose:** Row-level exception store. Every single flagged record from `silver_ev_operations` lands here — one row per detected exception per charger per minute. This is the source table that all other exception tables and rollups are built from.

**Why it exists:** Provides full audit trail. You can always trace back to the exact charger, timestamp, and original field values for any exception. Power BI anomaly drill-through links to this table.

**Key columns added via ALTER:**

| Column | Type | Description |
|---|---|---|
| `ingestion_timestamp` | DATETIME | When this exception was written — **critical for PL_04's Lookup query to filter by date** |
| `exception_category` | VARCHAR(50) | One of: `NULL_INJECTION`, `FAULT_STATE`, `LOGICAL_ANOMALY`, `PACKET_DROP_GAP` |
| `exception_type` | VARCHAR(100) | Specific tag: `BILLING_NULL`, `THERMAL_OVERLOAD_SHUTDOWN`, `USER_ID_MISSING`, etc. |
| `exception_severity` | VARCHAR(20) | `Critical`, `High`, `Low` — `fault_severity` only covers faults; this covers all categories |

**Populated by:** `usp_Load_Gold_EV_Exceptions` — 10 separate INSERT blocks, one per exception type.

---

### 2. `gold_ev_exception_summary`

**Purpose:** Daily aggregated rollup of all exceptions, grouped by category, type, and severity. This is the **primary table that PL_04's `Lookup_Exception_Rate` activity queries** to decide whether to fire the Logic App alert.

**Why it exists:** Querying the full row-level `gold_ev_exceptions` table for a monitoring check is expensive as data grows (millions of rows across many dates). This summary table reduces PL_04's lookup to a single small aggregation of ~10–15 rows per day. It also feeds the Power BI Data Quality Summary page.

**Key columns:**

| Column | Description |
|---|---|
| `data_date` | The date this summary covers — PL_04 filters on this |
| `exception_category` | Category of this group |
| `exception_type` | Specific exception type in this group |
| `exception_severity` | Severity of this group |
| `charger_count` | How many distinct chargers were affected |
| `exception_row_count` | How many rows were flagged |
| `total_lost_revenue_inr` | Sum of lost revenue across all rows in this group |
| `total_customers_lost` | Sum of customers lost |
| `total_downtime_mins` | Sum of downtime minutes |
| `pct_of_daily_rows` | This group's exception count as % of total silver rows for the day |

**PL_04 reads it like this:**
```sql
SELECT
    SUM(exception_row_count)                                            AS ExceptionCount,
    SUM(CASE WHEN exception_severity = 'Critical' THEN exception_row_count ELSE 0 END) AS CriticalCount,
    MAX(pct_of_daily_rows)                                              AS MaxExceptionRate
FROM dbo.gold_ev_exception_summary
WHERE data_date = '@pipeline_date'
```
PL_04 fires the Logic App alert if `MaxExceptionRate > 70%` **OR** `CriticalCount > 0`.

**Populated by:** Final ROLLUP 1 block in `usp_Load_Gold_EV_Exceptions`.

### 3. `gold_ev_fault_timeline`

**Purpose:** Fault-only narrow table. Contains one row per faulted minute per charger with full financial and operational context. This table is dedicated to Power BI's **Page 04 — Faults & Revenue Impact** dashboard.

**Why it exists:** The full `gold_ev_exceptions` table contains all categories mixed together. Power BI fault visuals (MTTR bar chart, fault type donut, downtime trend, revenue impact) need fault-only rows with financial fields readily available — no filtering overhead, no joins. This table is optimised with indexes on `(data_date, fault_severity)`, `(charger_id, data_date)`, and `(zone, data_date)` for fast slicer response.

**Key columns:**

| Column | Description |
|---|---|
| `error_code` | Fault code: `THERMAL_OVERLOAD_SHUTDOWN`, `GROUND_FAULT`, `CABLE_FAULT`, etc. |
| `fault_severity` | `Critical`, `High`, or `Low` — from source data |
| `is_repeat_fault` | 1 if this same fault code previously fired on this charger |
| `mttr_estimate_mins` | Mean time to repair from fault taxonomy |
| `downtime_mins_today` | Running total of downtime for this charger today |
| `connector_temp_c` | Temperature at time of fault — context for THERMAL faults |
| `peak_hour` | 1 if fault occurred during 08–10 or 17–21 (highest customer loss) |
| `fault_lost_revenue_inr` | Revenue lost this minute due to fault (power_kw × rev_rate × impact_multiplier) |
| `customers_lost` | 1.0/min during peak, 0.4/min off-peak |

**Fault codes and their severities (from data_gen.py):**

| Error Code | Severity | MTTR (mins) | Revenue Multiplier |
|---|---|---|---|
| `GROUND_FAULT` | Critical | 240 | 4.0× |
| `CABLE_FAULT` | Critical | 180 | 3.5× |
| `THERMAL_OVERLOAD_SHUTDOWN` | Critical | 120 | 3.0× |
| `POWER_FAILURE` | High | 90 | 2.5× |
| `PHASE_IMBALANCE_DETECTED` | High | 60 | 2.0× |
| `COMM_LOSS` | High | 45 | 1.8× |
| `ICE_VEHICLE_DETECTED` | Low | 10 | 0.3× |
| `AUTH_ERROR` | Low | 5 | 0.5× |

**Populated by:** CATEGORY 2 FAULT_STATE block in `usp_Load_Gold_EV_Exceptions` (same query that writes to `gold_ev_exceptions`, written twice).

### 4. `gold_ev_charger_exception_profile`

**Purpose:** Per-charger daily health rollup. One row per charger per day summarising every type of exception that occurred on that charger. Powers the **charger health leaderboard** and **System Health panel** on Page 06 — Charger Diagnostics.

**Why it exists:** Power BI's charger diagnostics page needs to rank all 300+ chargers by health score, highlight high-risk chargers in red, and show a component-level breakdown (billing health, sensor health, BMS health, fault count) per charger. Calculating this live from row-level exceptions on every Power BI refresh would be too slow. This pre-aggregated table makes all those visuals instant.

**Key columns:**

| Column | Description |
|---|---|
| `total_exceptions` | All exception rows for this charger today |
| `critical_exceptions` | Count of Critical severity rows |
| `fault_count` | Rows where `exception_category = FAULT_STATE` |
| `repeat_fault_count` | Times the same fault recurred |
| `billing_null_count` | Billing NULL rows |
| `sensor_null_count` | Voltage + current + thermal + ambient NULL rows combined |
| `bms_null_count` | Battery BMS NULL rows |
| `user_id_null_count` | Sessions with missing user identity |
| `packet_drop_count` | Gap rows from `gold_ev_packet_drop_gaps` for this charger |
| `exception_rate_pct` | This charger's exceptions ÷ its total rows × 100 |
| `is_high_risk` | **1** if `critical_exceptions > 0` OR `exception_rate_pct > 20%` — drives Power BI red flag |

**Constraint:** `UNIQUE (charger_id, data_date)` — one profile row per charger per day, prevents duplicates on re-run.

**Populated by:** ROLLUP 2 block in `usp_Load_Gold_EV_Exceptions`.

---

### 5. `gold_ev_packet_drop_gaps`

**Purpose:** Captures the **1% packet drop** simulated by `data_gen.py`. These rows represent minutes where a charger's heartbeat never arrived — they do not exist in `silver_ev_operations` at all, so they cannot appear in `gold_ev_exceptions`. This is the only table that detects this category of data loss.

**Why it exists:** Packet drops are silent failures — no row, no NULL, nothing to flag in standard NULL checks. The only way to detect them is to compare **expected timestamps** (every charger should emit exactly one row per minute) against **actual timestamps** using a LAG window function. This table records every detected gap with its duration and estimated revenue impact.

**How gap detection works:**
```sql
-- For each charger, find consecutive readings more than 1 minute apart
LAG(timestamp) OVER (PARTITION BY charger_id ORDER BY timestamp) AS prev_ts
-- If DATEDIFF(MINUTE, prev_ts, curr_ts) > 1 → gap exists
-- gap_duration_mins = DATEDIFF - 1 (the missing minutes in between)
```

**Key columns:**

| Column | Description |
|---|---|
| `expected_timestamp` | The specific minute that should exist but doesn't |
| `prev_timestamp` | Last recorded reading before the gap |
| `next_timestamp` | First recorded reading after the gap |
| `gap_duration_mins` | How many minutes were missing |
| `estimated_lost_revenue` | gap_duration_mins × avg revenue per minute for that charger |

**Populated by:** CATEGORY 4 PACKET_DROP_GAP block in `usp_Load_Gold_EV_Exceptions`.

## Stored Procedure: `usp_Load_Gold_EV_Exceptions`

**Called by:** PL_06 (Gold Layer pipeline), which runs after PL_05 (Silver load) and before PL_04 (Exception monitoring).

**Input parameter:** `@pipeline_date DATE` — the date to process, passed from the pipeline.

**What it does (in order):**

| Step | Action |
|---|---|
| 1 | **CLEANUP** — Deletes all existing rows for `@pipeline_date` across all 5 tables (idempotent — safe to re-run) |
| 2–8 | **NULL_INJECTION INSERTs** — 7 separate blocks, one per NULL scenario, each with deduplication guards |
| 9 | **FAULT_STATE INSERT** — Writes faulted rows to `gold_ev_exceptions` |
| 10 | **FAULT_STATE INSERT** — Writes same faulted rows to `gold_ev_fault_timeline` (narrow copy) |
| 11 | **LOGICAL_ANOMALY — ZERO_ENERGY_CHARGING** — Charging sessions with no energy delivered |
| 12 | **LOGICAL_ANOMALY — REPEAT_FAULT** — Same fault code recurring on same charger |
| 13 | **LOGICAL_ANOMALY — PEAK_HOUR_FAULT** — Critical category: faults during 08–10 or 17–21 |
| 14 | **PACKET_DROP_GAP** — LAG-based gap detection → `gold_ev_packet_drop_gaps` |
| 15 | **ROLLUP 1** — Aggregates `gold_ev_exceptions` into `gold_ev_exception_summary` |
| 16 | **ROLLUP 2** — Aggregates per-charger counts into `gold_ev_charger_exception_profile` |
| 17 | **RETURN** — Final SELECT returning row counts from all 5 tables (used by PL_06's Lookup activity for logging) |

**Deduplication guards:** NULL injection blocks include `AND electricity_cost_inr IS NOT NULL` style guards to prevent the same row being flagged for multiple NULL types simultaneously. For example, a row with billing NULL is not also flagged as a thermal sensor NULL — billing takes priority since it's the higher-impact failure.

## How All 5 Tables Connect to the Pipeline

```
silver_ev_operations
        │
        ▼
PL_06 calls usp_Load_Gold_EV_Exceptions(@pipeline_date)
        │
        ├──► gold_ev_exceptions              (row-level, all categories)
        │         └──► gold_ev_exception_summary     (daily rollup)
        │         └──► gold_ev_charger_exception_profile  (per-charger rollup)
        │
        ├──► gold_ev_fault_timeline          (fault-only, Power BI Page 04)
        │
        └──► gold_ev_packet_drop_gaps        (gap detection, 1% drop)
                │
                ▼
        PL_04 Lookup_Exception_Rate
        queries gold_ev_exception_summary
                │
                ├── MaxExceptionRate > 70% ?
                ├── CriticalCount > 0 ?
                │
                └── YES → THROW 50020 → Log_Exception_Breach → Send_Exception_Alert (Logic App)
                    NO  → Log_Exception_OK
```

## Full Execution Chain (Master Pipeline)

```
PL_01  Raw Ingestion         ADLS → raw_ev_telemetry
PL_03  Data Quality          Validates raw_ev_telemetry (row counts, NULLs, ranges)
PL_02  Raw → Staging         raw_ev_telemetry → stg_ev_telemetry (Data Flow)
PL_05  Staging → Silver      stg_ev_telemetry → silver_ev_operations (Stored Proc)
PL_06  Silver → Gold         silver_ev_operations → all 5 exception tables (usp_Load_Gold_EV_Exceptions)
PL_04  Exception Monitoring  Reads gold_ev_exception_summary → alerts if threshold breached
```
